## Architecture

Three deployables plus a database, split so that LLM access is isolated from business logic:

```
frontend/          Angular 17+ SPA — REST + JWT to the .NET API
backend-dotnet/     .NET 8 Web API — auth, roles, orchestration, persistence
ai-service-python/  FastAPI service — the only component that calls the LLM provider (DeepInfra)
MySQL 8            users, roles, chat sessions, messages, usage logs
```

Request flow for a chat message: Angular → `.NET POST /api/chat/sessions/{id}/messages` → validate session ownership → persist user message → load recent history → `.NET` calls `Python POST /generate` (typed `HttpClient`, `X-Internal-Key` header) → Python calls the LLM → `.NET` persists assistant message + a `UsageLog` row → returns `{ userMessage, assistantMessage }`.

Key rules that span components:
- The Python service **never** talks to MySQL and has no user concept. It is stateless: `.NET` sends the full history and prompt on every call.
- Python is authenticated only by a shared `INTERNAL_API_KEY` via the `X-Internal-Key` header — it must never be exposed to the browser.
- A Python failure (timeout, rate limit, upstream error) must surface to Angular as `503`, never `500`, and the user message stays persisted.
- Timeouts are layered and must stay nested: Python's LLM call (`llm_client.py`: `timeout=25`, `max_retries=1`, so about 50s worst case) must finish before .NET's `PythonAiClient` gives up (60s, `Program.cs`). If the inner budget exceeds the outer one, the user waits the full 60s on "Thinking…" and Python's clean error is never delivered. This really happened with the SDK's default `max_retries=2` at 30s. `test_llm_client_worst_case_fits_inside_dotnet_timeout` guards it.
- Error responses from `.NET` use a consistent shape: `{ "error": { "code", "message" } }` - always, including unhandled exceptions (`ExceptionHandlingMiddleware`), missing/invalid-token `401`s and wrong-role `403`s (`JwtBearerEvents.OnChallenge`/`OnForbidden` in `Program.cs` - these bypass MVC entirely by default, which is what made them easy to miss), and unmatched routes (`app.MapFallback`).
- JWT carries `sub`, `email`, `role`. Client-side JWT decoding is for UI conditionals only; real authorization is server-side (`[Authorize(Roles = "Admin")]`).
- Session ownership is enforced on every chat endpoint: a user may only touch their own sessions unless they are `Admin`.
- **(Enforced since Phase 10; delete and typing follow in Phase 13)** Direct messages are private: an `Admin` has no special access and gets `404` for a conversation they are not part of, exactly like anyone else. User search is by name only and never returns emails.
- **All dates are UTC.** The database stores UTC in `datetime(6)` (no zone), so every `DateTime` column goes through `UtcDateTimeConverter` (marks values UTC on read, so JSON carries a `Z`) and entities set `CreatedAt = DateTime.UtcNow` in code. Without this, browsers outside UTC show every reloaded time shifted by their offset. Always use `DateTime.UtcNow`, never `DateTime.Now`; a test (`EveryDateColumnInTheModel_UsesTheUtcConverter_SoNoneCanBeMissed`) guards new columns.
- **(Built in Phase 17)** Password-reset email goes through `IEmailQueue`: RabbitMQ when `RabbitMq:Host` is set, otherwise sent inline. The `forgot-password` answer is the same generic `200` in every case (known or unknown email, queue or send failure), so no outcome may ever surface as a different status. RabbitMQ and Redis are internal-only containers (no published ports); the queued message holds a raw reset link.
- **(Built in Phase 11)** Presence (who is online) is an in-memory singleton (`InMemoryPresenceTracker`), so the `api` must stay at **1 replica**. **Phase 16** replaces it with Redis (plus the SignalR backplane), which lifts that limit.
- **(Planned, Phase 18)** With `Chat:AsyncReplies` on, an LLM failure no longer surfaces as `503` on the send request; it arrives as the SignalR `AssistantFailed` event and the job is marked failed. `503` still applies when the broker itself is unreachable at publish time (user message stays persisted). The nested-timeouts rule still governs the consumer's call to Python.

## Cross-service contracts

`.NET → Python`: `POST /generate` with `{ session_id, history: [{role, content}], prompt }`
`Python → .NET`: `{ reply, tokens_used }`
`.NET → Angular` (send message): `{ userMessage, assistantMessage }`
**`.NET → Angular` direct-chat contracts** (all built: the REST shapes since Phase 10; the hub events `MessageReceived`, `MessageStatusChanged` and `MessagesRead` and `POST .../read` since Phase 11; `PeerTyping`, `MessageDeleted`, `PeerPresenceChanged` and `DELETE .../messages/{messageId}` since Phase 13): `GET /api/direct/users?search=` → `[{ id, name }]`; `GET /api/direct/conversations` → `[{ id, peer: { id, name }, lastMessage, unreadCount, peerOnline, peerLastSeenAt }]`; direct message → `{ id, conversationId, senderId, content, createdAt, status: "sent" | "delivered" | "read", deleted }`. SignalR hub `/hubs/direct`, server → client: `MessageReceived`, `MessageStatusChanged`, `MessagesRead`, `MessageDeleted`, `PeerTyping`, `PeerPresenceChanged`; client → server: `Typing(conversationId)`. The hub JWT travels as the `access_token` query string. The direct-chat contracts above are now all built; the README section is the source of truth.
**Planned (Phase 18) change to the send-message contract**, only when `Chat:AsyncReplies` is on: `202` `{ userMessage, replyStatus: "pending", jobId }`, then SignalR `AssistantReplied { jobId, assistantMessage }` or `AssistantFailed { jobId, error }`. `.NET → Python` (`POST /generate`) is unchanged.

Changing any of these requires updating both sides and the schema section of `README.md`.

## Testing expectations

Done as of Phase 8 - keep new tests consistent with these patterns:
- **`.NET`** (`backend-dotnet/tests/AiChatAssistant.Api.Tests/`): controller tests mock `IPythonAiClient`/`ITokenService` with Moq, but use the *real* FluentValidation validators and a real (`EntityFrameworkCore.InMemory`) `AppDbContext` - only the LLM/token-issuance boundary is faked. Build a caller identity with `TestSupport/ClaimsPrincipalFactory.Create(userId, email, ...roles)`, not a hand-rolled `ClaimsPrincipal` - it shapes claims the way they actually look *after* JWT validation (`role` remapped to `ClaimTypes.Role`, etc.), not the raw pre-validation JWT shape.
- **Python** (`ai-service-python/tests/`): monkeypatch `app.services.llm_client._client.chat.completions.create` - never call DeepInfra for real. `conftest.py` sets fake `DEEPINFRA_API_KEY`/`INTERNAL_API_KEY` via `os.environ.setdefault` so tests don't need a real `.env`. `pytest.ini` sets `pythonpath = .` (required: `app/` and `tests/` are siblings).
- **.NET (email queue)**: the consumer's decisions live in `PasswordResetEmailProcessor` and are tested with a mocked `IEmailSender` and a hand-moved `TimeProvider`; DI wiring is tested with a bare `ServiceCollection` (no host, no broker). Never connect a unit test to a real RabbitMQ; the queue glue is checked in the Docker run instead (see `TESTING.md` section 13).
- **Angular (direct chat)**: test `DirectStateService` with a fake `DirectChatService` (jasmine spies returning `of(...)`) and a fake `DirectHubService` made of plain `Subject`s, fire "live" events by hand, and fake tab visibility with `spyOnProperty(document, 'visibilityState', 'get')`.
